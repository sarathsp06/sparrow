New to Sparrow? This guide shows you how to change the shape of a webhook
payload *before* it's delivered — no code, no proxy service, just a small
template you write once per subscription.

## What is a transform, and why would I want one?

A webhook payload is just a chunk of JSON. The problem is that the system
Sparrow delivers to rarely wants the *exact* JSON your event started with:

- Slack wants a `{"text": "..."}` message, not your raw event.
- Your billing system wants amounts in **cents**, but your event has **dollars**.
- A legacy endpoint wants a flat object, but your event is deeply nested.
- A partner should only see three fields, not your entire internal record.

A **transform** solves this. You attach a small template to a subscription, and
Sparrow runs your event through it to produce the body that actually gets sent.

<Aside type="tip" title="One subscription, one shape">
Every subscription can have its own transform. The *same* event can be
delivered to Slack as a chat message and to your data warehouse as flat JSON —
each subscription reshapes it independently.
</Aside>

## Where the transform lives

When you create or update a subscription, set its `transform_template` field.
That's it — Sparrow handles the rest at delivery time.

## The mental model (read this first)

A template **receives your event** and **prints text**. Whatever text it prints
becomes the delivered body. Your event is available through these fields:

| Field | What it is |
|-------|------------|
| `.payload` | Your event's data (the JSON you pushed) |
| `.event_name` | The event type, e.g. `payment.succeeded` |
| `.event_id` | Unique ID for this event |
| `.timestamp` | When the event happened |
| `.attempt` | Which delivery attempt this is |

So `{{ .payload.customer.email }}` reads the `customer.email` field out of your
event, and `{{ .event_name }}` prints the event type.

<Aside type="caution" title="A missing field is an error">
By default a template that reads a field the payload does not have **fails**
instead of printing `<no value>`, so a field removed from an event type's
schema cannot silently put a wrong value in the body. Read fields that may be
absent with `dig` or `index`, which never fail on a missing key:
`{{ dig "coupon" "" .payload }}` or `{{ index .payload "coupon" }}`.
`default` does not help here: in `default "x" .payload.coupon` the lookup fails
before `default` runs. See [When a template fails](#when-a-template-fails).
</Aside>

<Aside type="caution" title="Templates print text — use `json` for JSON">
A template outputs raw text. If you want to deliver **valid JSON**, build a map
or list and pipe it through the `json` function (shown below). Don't hand-write
JSON with `{}` and quotes around your values — you'll hit escaping bugs the
moment a value contains a quote. Let `json` do it.
</Aside>

## Try it before you ship it

You don't have to guess. Every example below is a complete command: paste it
into a terminal and it prints the delivered body. You need the
[`sparrow` CLI](/sparrow/satellites/cli/) installed; the first two steps work
without a running server.

<Steps>

1. **List the available helpers**, or read one helper's full docs:

   ```bash
   sparrow functions
   ```

   ```bash
   sparrow functions dig
   ```

   `functions` asks the server (`--url` or `sparrow init` point it at one).

2. **Render a template against a sample payload, entirely offline.** The CLI
   embeds the same engine the delivery worker uses. Pass `-` to read the
   template from stdin, so a heredoc keeps the template and its sample
   together:

   ```bash
   sparrow template test - --event-name payment.succeeded --payload '{"amount": 4200}' <<'EOF'
   {{ dict "id" .event_id "amount" .payload.amount | json }}
   EOF
   ```

   Prints:

   ```json
   {"amount":4200,"id":"evt_sample"}
   ```

   It renders strictly, as a subscription does by default: read a field the
   payload lacks and the command fails with the same error a delivery would
   record. Add `--missing-key zero` to render missing fields as `<no value>`
   instead, like a subscription with `template_missing_key: zero`. Pass
   `--payload @event.json` to use a file, or a template file instead of `-`.

3. **Dry-run against the event type's stored sample payload on the server.**
   This renders with the sample Sparrow derived from the event type's schema,
   so it catches a template that reads a field the schema does not define.
   There is no CLI command for it yet; it is one API call:

   ```bash
   curl -s -X POST http://localhost:8080/v1/subscriptions:testTemplate \
     -H 'Content-Type: application/json' \
     -d '{
       "event_name": "payment.succeeded",
       "template": "{{ dict \"id\" .event_id \"amount\" .payload.amount | json }}"
     }'
   ```

   Returns `{"rendered": "{\"amount\":551,\"id\":\"dry-run-event-id\"}"}` (the
   amount is whatever the generated sample holds). It needs an event type
   registered **with a schema**: `sparrow events payment.succeeded` shows the
   schema and sample payload, and an event type auto-created by a push has
   neither, so register one first if the call answers 404:

   ```bash
   curl -s -X POST http://localhost:8080/v1/event-types \
     -H 'Content-Type: application/json' \
     -d '{
       "name": "payment.succeeded",
       "description": "A payment was captured",
       "event_schema": {
         "type": "object",
         "properties": {
           "id": {"type": "string"},
           "amount": {"type": "integer"},
           "currency": {"type": "string"}
         },
         "required": ["id", "amount", "currency"]
       }
     }'
   ```

</Steps>

## Real-world examples

Each example shows the **incoming event**, the **template** you'd set on the
subscription, and the **delivered result**, as one command you can run. The
part between `<<'EOF'` and `EOF` is the template; the `--payload` is the
incoming `.payload`. To ship one, copy the template into the subscription's
`transform_template`.

### 1. Send only the fields a partner needs

**Problem:** your event has 30 internal fields, but a partner should only see
three.

```bash
sparrow template test - --event-name payment.succeeded \
  --payload '{"id": "evt_123", "amount": 4200, "internal_notes": "…", "secret": "…"}' <<'EOF'
{{ dict "id" .payload.id "amount" .payload.amount "event" .event_name | json }}
EOF
```

**Delivered:**

```json
{"amount":4200,"event":"payment.succeeded","id":"evt_123"}
```

`dict` builds an object from `"key" value` pairs; `json` turns it into JSON.

### 2. Post a message to Slack

**Problem:** Slack's Incoming Webhooks expect `{"text": "..."}`.

```bash
sparrow template test - \
  --payload '{"customer": {"name": "Ada"}, "amount": 4200, "currency": "usd"}' <<'EOF'
{{ dict "text" (printf "%s paid %s %.2f" (dig "customer" "name" "Someone" .payload) (upper .payload.currency) (div .payload.amount 100)) | json }}
EOF
```

**Delivered:**

```json
{"text":"Ada paid USD 42.00"}
```

Here `dig` safely reads `customer.name` (falling back to `"Someone"` if it's
missing), `div` converts cents to dollars, and `printf` formats the sentence.

### 3. Convert dollars to cents for a billing system

**Problem:** your event has amounts in dollars; the target wants integer cents.

```bash
sparrow template test - \
  --payload '{"customer": {"id": "cus_9"}, "amount": 42.5, "currency": "usd"}' <<'EOF'
{{ dict "user" (dig "customer" "id" "" .payload) "amount_cents" (toInt (mul .payload.amount 100)) "currency" .payload.currency | json }}
EOF
```

**Delivered:**

```json
{"amount_cents":4250,"currency":"usd","user":"cus_9"}
```

`mul` multiplies, `toInt` drops the decimal so you get a clean integer.

### 4. Flatten a nested payload for a legacy endpoint

**Problem:** an old system wants a flat object, but your data is nested.

```bash
sparrow template test - \
  --payload '{"customer": {"id": "c1", "email": "ada@example.com"}, "order": {"total": 99.5}}' <<'EOF'
{{ dict "customer_id" (dig "customer" "id" "" .payload) "email" (dig "customer" "email" "" .payload) "total" (dig "order" "total" 0 .payload) | json }}
EOF
```

**Delivered:**

```json
{"customer_id":"c1","email":"ada@example.com","total":99.5}
```

`dig` walks a path of keys and returns your default if any part is missing — so
one absent field never breaks the whole delivery.

### 5. Summarize a list of items

**Problem:** your event has an array of line items; you only want the SKUs.

```bash
sparrow template test - \
  --payload '{"items": [{"sku": "A"}, {"sku": "B"}, {"sku": "C"}]}' <<'EOF'
{{ $skus := list }}{{ range .payload.items }}{{ $skus = append $skus .sku }}{{ end }}{{ dict "skus" $skus | json }}
EOF
```

**Delivered:**

```json
{"skus":["A","B","C"]}
```

`range` loops over the array; `append` collects each SKU into a growing list.

### 6. Add a constant or computed field

**Problem:** you want to pass the whole payload through, but tag it with extra
metadata.

```bash
sparrow template test - --payload '{"id": "evt_123", "amount": 4200}' <<'EOF'
{{ merge .payload (dict "source" "sparrow" "delivered_at" (formatTime "2006-01-02T15:04:05Z07:00" now)) | json }}
EOF
```

**Delivered:** your original payload, plus `"source"` and `"delivered_at"`:

```json
{"amount":4200,"delivered_at":"2026-10-06T14:45:37Z","id":"evt_123","source":"sparrow"}
```

`merge` combines maps; later keys win, and the originals are left untouched.

### 7. Provide safe defaults for optional fields

**Problem:** some events are missing optional fields, and you want sensible
fallbacks instead of empty values.

```bash
sparrow template test - --payload '{"plan": ""}' <<'EOF'
{{ dict "name" (dig "customer" "name" "Guest" .payload) "plan" (default "free" (index .payload "plan")) | json }}
EOF
```

**Delivered:**

```json
{"name":"Guest","plan":"free"}
```

`dig` covers missing nested keys. `index` reads a top-level key without failing
when it is absent, and `default` then covers a field that is missing or
present but empty. Compare what strict rendering does with a plain field read
on the same payload:

```bash
sparrow template test - --payload '{"plan": ""}' <<'EOF'
{{ .payload.customer.name }}
EOF
```

```
sparrow: template error: ... map has no entry for key "customer"
```

## Good to know

- **Transforms run at delivery**, on the way out. They don't change what Sparrow
  stores or how it fans out — only the body each subscription receives.
- **A template that fails is visible.** See [When a template fails](#when-a-template-fails).
- **There are limits.** Output is capped at **1 MB** and execution at **5
  seconds** per transform, so a runaway template can't stall a worker.
- **Why Go templates and not JavaScript?** They're parsed once and cached, run
  with almost no overhead, add zero dependencies, and are safe to share across
  every delivery worker — a deliberate choice for a small memory footprint and
  high throughput. See [Why Sparrow](/sparrow/getting-started/why-sparrow/).

## When a template fails

A template fails when it reads a field the payload does not have (with the
default `template_missing_key: error`), calls a function with the wrong kind of
value, or exceeds the limits above. Two settings on the subscription decide
what happens.

| Setting | Values |
|---------|--------|
| `on_transform_error` | `fail` (default): nothing is sent. The delivery is marked failed with error category `template_error`, is **not retried automatically**, and keeps the error in `template_error`. `fallback`: the standard event envelope is sent instead, and the error is still recorded on the delivery. |
| `template_missing_key` | `error` (default): reading a missing field fails the template. `zero`: it prints `<no value>` and the delivery goes out. |

Both are set on the subscription. Find the subscription's id from its webhook
(`sparrow webhooks` lists webhook ids), then patch it:

```bash
sparrow webhooks "$WEBHOOK_ID" -o json | jq -r '.subscriptions[] | "\(.subscription_id) \(.event_name)"'
```

```bash
curl -s -X PATCH "http://localhost:8080/v1/consumers/default/subscriptions/$SUBSCRIPTION_ID" \
  -H 'Content-Type: application/json' \
  -d '{"on_transform_error": "fallback", "template_missing_key": "zero"}'
```

A template error is a problem on the sending side, not with the receiving
system, so it **never counts toward the webhook's health** and raises no health
alert. It is counted in the `sparrow_template_errors_total` metric.

To recover, fix the template, then retry: one delivery with
`POST /v1/consumers/{consumer}/deliveries/{delivery_id}:retry`, or all of them
by listing `?status=failed&error_category=template_error&prepare_retry=true`
and starting a batch retry. Every attempt renders the subscription's current
template, so the retry uses the fixed one. In the UI, filter Deliveries by the
**Template Error** category.

When an event type's schema changes, Sparrow checks every subscription's
template against the new schema before the change is written; see
[Event Type Versions](/sparrow/guides/event-type-versioning/#breaking-changes).
