Satellites are companion tools that **orbit the core** — they use Sparrow, they
never reach inside it. Every satellite talks to the same public REST API and
signed-webhook contract you do, so the delivery pipeline (matching, retries,
signing, audit trail) stays one small, boring server. Delete every satellite
and Sparrow still works; add your own and it is a first-class citizen.

## The satellites

| Satellite | What it does | Direction |
| --- | --- | --- |
| [CLI](/sparrow/satellites/cli/) | Push events, tail deliveries, receive webhooks locally, apply recipes, debug templates — the terminal loop | both |
| [Recipes](/sparrow/satellites/recipes/) | Adapters as config: one YAML file turns deliveries into Slack, Discord, ntfy, PagerDuty, ClickHouse, Twilio, SendGrid, or CloudEvents payloads — rendered server-side, nothing extra runs | out |
| [Sources](/sparrow/satellites/sources/) | Cron schedules plus webhook receivers that verify the provider's signature and re-publish as typed Sparrow events — see the Sources page for the current provider list | in |
| [Sinks](/sparrow/satellites/sinks/) | A signed-delivery receiver that forwards to destinations that don't take webhooks: SMTP email, S3/MinIO archives, and OpenTelemetry log records | out |

Each page explains the satellite's technical path — exactly which API calls it
makes, how signatures are verified, and what happens per delivery.

## Example: Stripe payments, end to end

One flow that uses three satellites, none of which needs code:

1. **Source:** `sparrow-sources` receives Stripe's `payment_intent.succeeded`
   webhook, checks the `Stripe-Signature`, and pushes
   `stripe.payment_intent.succeeded` into Sparrow with labels `source=stripe`
   and `livemode=true`. See [Sources](/sparrow/satellites/sources/#stripe).
2. **Recipe:** a webhook created with `sparrow use slack --event stripe.payment_intent.succeeded`
   posts each payment to a Slack channel. Sparrow renders the message itself;
   nothing else runs. See [Recipes](/sparrow/satellites/recipes/#slack).
3. **Sink:** a second webhook points at `sparrow-sinks`, whose S3 sink writes
   each delivery's envelope to
   `events/stripe.payment_intent.succeeded/2026/10/08/<event_id>.json` for
   later audit queries. See [Sinks](/sparrow/satellites/sinks/#s3).

Sparrow signs, retries and records each of the two deliveries on its own, so a
Slack outage doesn't hold up the archive. Stripe may deliver the same event
twice; deduplicate downstream on the payload's `id`.

## The contract

Anything you build against the same three rules inherits the whole pipeline:

1. **Public API only** — no database access, no server internals.
2. **Verify signatures** — check the Standard Webhooks headers before trusting a delivery.
3. **Fail loudly, stay stateless** — return non-2xx and let Sparrow's retries do the work.

:::note
Sparrow blocks private-network delivery URLs by default (SSRF guard). For a
local receiver (`sparrow listen`, a dev sink, a laptop endpoint), start the
**server** with `SPARROW_ALLOW_PRIVATE_NETWORKS=true`. For a sink on an
internal network, list that network in `SPARROW_ALLOWED_NETWORKS` instead.
:::
