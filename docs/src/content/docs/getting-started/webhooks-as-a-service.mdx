**Sparrow is open-source webhooks as a service that you host yourself.** Your
application publishes an event once with one `POST`; Sparrow fans it out to
every subscribed endpoint, signs each request, retries failures, tracks the
health of each endpoint, and keeps a full delivery history. It is one Go binary
and PostgreSQL, MIT-licensed, with no per-message pricing.

## What a webhook service does

Sending one HTTP request is easy. Sending webhooks to customers reliably is
not, which is why "webhooks as a service" exists as a product category. A
webhook service takes over:

- **Fan-out**: one event, delivered to every endpoint subscribed to its type.
- **Retries**: exponential backoff, separating retryable failures (timeouts,
  5xx, 429) from permanent ones.
- **Signing**: a signature on every request so receivers can verify it came
  from you ([Standard Webhooks](/sparrow/guides/verify-signatures/)).
- **Endpoint health**: noticing a receiver that has been failing for hours and
  pausing it without losing what was sent to it.
- **Delivery log and replay**: what was sent, what the receiver answered, and
  a way to retry it.
- **Customer self-service**: a portal where your customers add endpoints,
  choose events and inspect their own deliveries.

Sparrow does all of these. See [How it works](/sparrow/getting-started/how-it-works/)
for the pipeline.

## Managed or self-hosted

There are two ways to get webhooks as a service:

<CardGrid>
  <Card title="Managed (SaaS)" icon="external">
    A vendor runs the delivery infrastructure. Nothing to operate; you pay per
    message or per tier, and every payload passes through the vendor's network.
  </Card>
  <Card title="Self-hosted (Sparrow)" icon="laptop">
    You run the service next to your application. Payloads never leave your
    network, there is no per-message price, and the only dependency is a
    PostgreSQL database you probably already operate.
  </Card>
</CardGrid>

Pick self-hosted when payloads must stay inside your network (regulated data,
internal systems), when message volume makes per-message pricing expensive, or
when you would rather run one more container than add a vendor. Pick managed
when you want no infrastructure at all.

## Sparrow at a glance

| | |
|---|---|
| **License** | MIT, every feature in the open-source code |
| **Runs as** | One Go binary or a ~15MB distroless Docker image |
| **Dependencies** | PostgreSQL only: the job queue ([River](https://riverqueue.com)) runs in it, no Redis or broker |
| **API** | REST with an OpenAPI 3.1 spec; generate a client in any language |
| **Signing** | Standard Webhooks, HMAC-SHA256 or Ed25519 |
| **Delivery** | At-least-once, classified retries, idempotent ingestion, per-endpoint rate limits |
| **Customer portal** | Embeddable, scoped to one consumer by an expiring token |
| **Payload transforms** | Go templates per subscription, plus ready-made [recipes](/sparrow/satellites/recipes/) for Slack, Discord, PagerDuty and others |
| **Observability** | OpenTelemetry traces, metrics and logs; Prometheus `/metrics` |

## Sparrow compared to other webhook services

Svix, Hookdeck and Convoy are the best-known webhook-as-a-service platforms.
In short:

- **Svix**: managed service with an open-source server. Sparrow is the closest
  match: Standard Webhooks signing and an embeddable customer portal, but MIT
  throughout, PostgreSQL-only, and self-hosted only.
- **Hookdeck**: mainly a managed platform (Outpost is its open-source, self-hosted
  part). Sparrow has no managed offering.
- **Convoy**: self-hostable under the Elastic License 2.0 and needs Redis.
  Sparrow is MIT and needs only PostgreSQL.

The full feature table, including where the alternatives are stronger, is in
[Why Sparrow](/sparrow/getting-started/why-sparrow/#feature-comparison).

## Try it

```bash
curl -O https://raw.githubusercontent.com/sarathsp06/sparrow/main/deploy/docker-compose.yml
docker compose up -d
```

This starts Sparrow and PostgreSQL for local evaluation, with the dashboard at
`http://localhost:8080`. Follow the [quickstart](/sparrow/getting-started/quickstart/) to register a
webhook and push your first event, or read [Installation](/sparrow/getting-started/installation/)
for the other ways to run it.
